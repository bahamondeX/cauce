# Proxy configuration

Cauce reads version 1 YAML from paths ending in `.yaml` or `.yml`. An explicit TOML path still uses the legacy layout. With no path, the native command uses `examples/cauce.yaml`. The current container and Compose examples continue passing their TOML paths explicitly.

```sh
cargo run --locked -- check examples/cauce.yaml
cargo run --locked -- examples/cauce.yaml
```

YAML starts with `version: 1`. Existing proxy fields go below `proxy`. Unknown fields, repeated mapping keys, extra documents and custom tags are rejected. The sample includes a YAML language server modeline for the [editor schema](../schemas/cauce.schema.json). Cauce also validates authority syntax, referential integrity, compatible limits, and configured TLS material at runtime. [Complete YAML example](../examples/cauce.yaml).

Duration names retain their units for interoperability with TOML. An integer in `headers_ms` means milliseconds, and an integer in `tcp_keepalive_secs` means seconds. The duration fields also accept whole-number values with `ms`, `s`, `m` or `h` suffixes. Conversion must fit the field and satisfy its configured limits. For example, `headers_ms: 5s` and `headers_ms: 5000` are equivalent.

Byte fields accept integer bytes or whole-number values with `B`, `KiB`,
`MiB` or `GiB` in YAML and TOML. The suffixes are binary units. For example,
`max_header_bytes: 32KiB` is 32,768 bytes. These units apply to header and
body limits, JSONL rotation size, and HTTP/2 window and send-buffer bytes.
Configuration preparation checks conversion and applies the field's
existing limits to the resulting integer.

Use an entire YAML scalar such as `"${CAUCE_SERVER_KEY_FILE}"` to load a value from the process environment. Substitution runs on parsed scalar values and never reparses variable contents as YAML. References work with string fields and unit-suffixed durations and sizes. An unset or non-Unicode reference rejects the candidate. The aggregate expansion budget is 1 MiB. YAML substitution and validation diagnostics omit resolved values. TLS PEM errors identify the failing operation. Use file paths for TLS private keys. Names and upstream or route IDs are operational labels that can appear in logs.

## Virtual hosts and locations

Use a lowercase exact authority, a leading wildcard such as `"*.example.test"`,
or a trailing wildcard such as `"mail.*"`. A wildcard consumes one or more
complete DNS labels. Supply the port in the pattern when the client sends it
in the authority. For example, `"*.example.test:8080"` matches
`tenant.example.test:8080`. Matching selects the exact authority first, then
the longest leading wildcard, then the longest trailing wildcard.

Choose `path_match: exact` for a literal path. The match ignores the query.
Set `path_prefix` to the path in either mode. Exact paths take priority within
the selected host. The default mode uses the longest segment-bounded prefix.
A host with no matching path returns 404. Match selection never falls through
to another virtual host. [Complete YAML example](../examples/wildcard-hosts.yaml).

Opt in to flat NGINX location precedence with `literal_prefix`,
`prefix_no_regex`, `regex`, and `regex_insensitive`. The first two use
`path_prefix` and match a literal byte prefix, including suffixes in the
same path segment. The regex modes use `path_pattern` in place of
`path_prefix`. Exact locations win first. The longest applicable
`prefix_no_regex` skips regex evaluation. Otherwise the first matching
regex in configuration order wins, then selection falls back to the
longest prefix. Existing `prefix` routes retain segment-aware matching.

Regexes use Rust's byte regex syntax with ASCII case folding. Each
pattern is limited to 256 bytes, with up to 16 patterns per configured
authority and 128 per configuration. Cauce compiles them before
publishing a generation. A malformed or oversized expression rejects a
reload. `cauce check` identifies the affected route. The match sees the validated request path
without the query. Named locations, nested locations, internal redirects,
PCRE-only features and NGINX URI normalization remain outside this subset.
[Advanced YAML example](../examples/advanced-locations.yaml).

Use route-local `headers.request` and `headers.response` with `set`
maps and `remove` lists. Edits run after hop-by-hop filtering. A set
replaces existing values for that header. Response edits apply to proxied
HTTP response headers. WebSocket upgrade responses, trailers and
responses generated by Cauce follow their own protocol handling.

Header names are case-insensitive. A direction accepts at most 16 edits
and 4 KiB of configured replacements. Cauce rejects duplicate edits,
non-printable values, and edits to routing, framing, forwarding,
request identity, trace context, WebSocket and gRPC protocol headers.
Transformed header maps still obey the configured request and response
limits. The migration preview translates static, location-local
`proxy_set_header` and `proxy_hide_header`. Variables and inheritance
require review. [Header policy YAML example](../examples/header-policies.yaml).

## Reload and rollback

Prepare the full candidate in a file next to the active configuration, retaining the same YAML or TOML extension. Run `cauce check` against the candidate, rename it over the active path on the same filesystem, and send the running process SIGHUP. The running process checks the listener, limits, HTTP/2 and logging settings for restart requirements and prepares certificates, trust stores, routes and upstreams before activating a generation. A rejected candidate leaves the current generation active.

Keep the last known valid file. To roll back an accepted change, atomically republish that file and signal SIGHUP again. A successful rollback creates a new generation. Existing streams complete with the leases they acquired before the reload. The status log records `reloaded` or `reload_rejected`.

To migrate manually from TOML, preserve the proxy values in a version 1 YAML file and validate it before swapping the process configuration path. To assess migration from NGINX, use the [pinned compatibility registry](../compatibility/nginx-oss.yaml). Its directive status describes the degree of Cauce overlap, including documented semantic differences.

## NGINX migration report

Run the offline report on an NGINX configuration:

```sh
uv run --no-project --with pyyaml python scripts/nginx-migration-report.py nginx.conf
uv run --no-project --with pyyaml python scripts/nginx-migration-report.py nginx.conf --preview candidate.yaml
cargo run --locked -- check candidate.yaml
```

The report identifies each directive's line, context, reference registrations, coverage and known semantic differences. The registry includes the pinned NGINX source release, njs HTTP and stream modules, and the nginx-acme module and its issuer-block directives. Analyze included files separately. Directive arguments stay out of the report. The preview accepts a single cleartext HTTP server with an explicit IPv4 listener, explicit DNS names or edge wildcards, and flat literal exact, prefix, or `^~` locations that proxy to literal IPv4 upstreams. Regex locations require manual migration because PCRE and Rust regex syntax differ. It generates a review-only file with Cauce defaults and records its confidence and a validation command. Review route matching, host forwarding, buffering, timeouts and capacity before use. Unsupported structures cause the preview command to exit unsuccessfully, and an existing output file is protected.

Regenerate the source inventory with `python3 scripts/nginx-inventory.py` or verify the generated file with `--check`. Pass `--tarball`, `--njs-tarball` and `--acme-tarball` to use local copies of the checksummed sources. Maintain Cauce feature statuses and test references in [nginx-coverage.json](../compatibility/nginx-coverage.json).

## Gateway policies

[Production gateway example](../examples/production-gateway.yaml) uses
the existing version-1 YAML model. The same fields are available in TOML.

- `real_ip` enables trusted peer CIDRs and selects `x_forwarded_for` or
  `x_real_ip`. Recursive X-Forwarded-For walks from right to left and
  stops at the first untrusted address. Repeated X-Forwarded-For fields
  follow wire order. Malformed, duplicated X-Real-IP or oversized input
  falls back to the socket peer. `preserve_trusted_chain` keeps the
  canonical trusted suffix and appends the socket peer.
- Route `action` accepts `rewrite`, `redirect` and `named`. Rewrites
  and redirects can use a bounded byte regex and `$1` through `$9`.
  `query: preserve` appends the original query to configured arguments.
  `query: replace` emits only configured arguments. A named route uses
  `path_match: named` and the location identifier in `path_pattern`.
  Conditional actions require an upstream for requests that miss their
  pattern. An unconditional route action may use `upstreams: []`.
- Upstream `weight` ranges from 1 to 64. Supported algorithms are
  `round_robin`, `least_inflight`, `weighted_round_robin`,
  `least_connections`, `weighted_least_connections`, `ip_hash`,
  `consistent_hash` and `power_of_two_choices`. Least-connection modes
  count active leases, including HTTP/2 streams. Hashing uses the
  resolved client address. Endpoint IDs are stable hash identities.
- Route `allow_clients` lists CIDRs. Route `rate_zone` references a named
  `rate_zones` entry. A `client_ip` key shares a client's budget across
  routes using the zone. A `route` key gives each route a separate
  budget. `rate_per_second` and `burst` define pace and excess capacity.
  An optional `max_delay_ms` enables bounded scheduling. `max_concurrent`
  limits active HTTP requests or streams. `reject_status` and
  `error_body` set the HTTP rejection. The separate
  `max_connections_per_peer` caps physical TCP sockets before TLS.
  Zone specifications and the peer cap require restart.

The NGINX migration preview also translates server-local
`set_real_ip_from`, `real_ip_header` and `real_ip_recursive`
with literal IPv4 or IPv6 addresses. It translates flat, static
origin-relative `return` redirects alongside proxied locations.
Complex rewrites, inherited policies and NGINX-specific balancing
and admission tables require review.
[Policy ordering](adr/0011-compiled-gateway-policies.md).

## Active upstream health

Add `health_check` to an upstream to gate selection on probe results. The
default `mode: http` sends GET to an origin-form `path` over that upstream's
HTTP/1.1 or HTTP/2 transport and accepts 2xx headers. `mode: grpc` requires
`protocol: http2` and uses the standard unary Health/Check RPC. Omit
`service` to check the whole server. The probe requires an uncompressed
SERVING message and successful gRPC trailers. Use `interval_ms`,
`timeout_ms`, `rise` and `fall` to control cadence and state transitions.

Upstreams with active checks start unavailable and become eligible after
`rise` successes. HTTP checks finish on response headers. gRPC checks
read at most a 1 KiB protobuf message, require successful trailers and
use the same absolute probe timeout. Secure HTTP/2 requires h2 ALPN and
uses the upstream trust configuration. A generation can configure up to
64 active checks, with at most four sockets active in its probe scheduler.
A reload restarts the checks for the new generation. Probes use separate
sockets from the user-data pools. [YAML example](../examples/http2-health.yaml)
[gRPC health protocol](https://github.com/grpc/grpc-proto/blob/master/grpc/health/v1/health.proto).
